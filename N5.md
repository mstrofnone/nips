NIP-N5
======

CLINK static payment pointers in the Namecoin `nostr` item
----------------------------------------------------------

`draft` `optional`

This NIP specifies how a Namecoin record carries CLINK static payment
pointers — [CLINK Offers][clink-offers] (`noffer1...`) and
[CLINK Debits][clink-debits] (`ndebit1...`) — so that wallets can resolve
a `.bit` (or `d/`/`id/`) identifier to a Lightning-payment endpoint
without DNS, HTTPS, or a public CA in the discovery path.

It builds on:

- NIP-N0 (the `nostr` item, `import`, `map` walker, encoding constraints).
- NIP-N1 (NIP-05 verification via Namecoin) — re-used here as the
  resolution primitive: the same merged Domain Name Object that NIP-N1
  reads `nostr.names` from also carries `nostr.clink_offer` and
  `nostr.clink_debit`.
- [CLINK Offers][clink-offers], [CLINK Debits][clink-debits].
- [ifa-0001][ifa-0001] (Namecoin Domain Name Object).

[clink-offers]: https://github.com/shocknet/CLINK/blob/main/specs/clink-offers.md
[clink-debits]: https://github.com/shocknet/CLINK/blob/main/specs/clink-debits.md
[ifa-0001]: https://github.com/namecoin/proposals/blob/master/ifa-0001.md

## Abstract

The CLINK specifications define a NIP-05 JSON extension in which a
`names`-style server response carries `clink_offer` and `clink_debit`
maps alongside the standard `names` map. This NIP states that a wallet
or client MAY treat the merged Domain Name Object returned by NIP-N1
resolution as a NIP-05 JSON response for the purposes of CLINK
discovery, including the optional `clink_offer` and `clink_debit`
mappings.

The intent is **zero new top-level Namecoin record keys** and **zero
new bytes on the CLINK wire**: this NIP only describes how an existing
wire format (CLINK's NIP-05 extension) is populated by an existing
identity substrate (NIP-N1 / ifa-0001).

## Identifier grammar

The identifier shapes recognised here are identical to NIP-N1
§"Identifier grammar". CLINK static pointers MAY be advertised for any
`<localpart>` that has a corresponding entry in `nostr.names`. The
sentinel local-part `_` (representing the bare `<name>.bit` /
`_@<name>.bit` form) is RECOMMENDED for the primary pointer.

## Wire format

After resolving `import` and walking `map` per NIP-N0 and NIP-N1, the
merged Domain Name Object MAY contain `nostr.clink_offer` and/or
`nostr.clink_debit` of shape:

```jsonc
{
  "nostr": {
    "names": {
      "_":     "<32-byte-hex-pubkey>",
      "alice": "<32-byte-hex-pubkey>"
    },
    "clink_offer": {
      "_":     "noffer1...",
      "alice": "noffer1..."
    },
    "clink_debit": {
      "_":     "ndebit1...",
      "alice": "ndebit1..."
    }
  }
}
```

`clink_offer` and `clink_debit` SHALL each be a JSON object whose keys
are local-parts and whose values are bech32-encoded TLV strings as
defined by [CLINK Offers][clink-offers] and [CLINK Debits][clink-debits]
respectively. The HRP MUST be `noffer` (for `clink_offer`) and
`ndebit` (for `clink_debit`); strings with any other HRP MUST be
rejected.

A local-part key in `clink_offer` or `clink_debit` SHOULD also appear
in `nostr.names`. Resolvers MAY surface an entry whose local-part has
no corresponding `nostr.names` key, but SHOULD warn the user that the
pointer is not bound to a Nostr identity on the same record.

### Scalar shorthand (optional)

If the only entry in `clink_offer` or `clink_debit` is the sentinel
`_`, publishers MAY use a bare string in place of the object:

```jsonc
{
  "nostr": {
    "clink_offer": "noffer1...",
    "clink_debit": "ndebit1..."
  }
}
```

A resolver receiving the scalar form MUST treat it as semantically
equivalent to `{"_": "<string>"}`. This shorthand exists solely to fit
the Namecoin 520-byte value limit; publishers with more than one
local-part MUST use the object form.

## Pricing-type and currency hints

The pricing-type flag (TLV 3), price (TLV 4), and currency code
(TLV 5) defined in [CLINK Offers][clink-offers] are carried inside the
bech32 string itself and MUST NOT be hoisted into separate top-level
fields on the Namecoin record. This keeps the on-chain shape compatible
with off-chain CLINK clients that already parse the bech32.

## Multi-pointer publication

A publisher MAY advertise more than one `noffer` for the same
local-part — e.g. one for fixed-price commerce and one with the
`zap` prefix for NIP-57 zaps — by factoring them onto a second
Namecoin name and referencing it via `import`. This is a special
case of the general NIP-N0 `import` mechanism and requires no new
syntax. Example: a small auxiliary name `d/cl-<base>` carrying just
the CLINK fields, imported from the base record's `dd/<base>`.

This is the recommended publication pattern for records that already
approach the 520-byte ceiling, and is what the reference deployment
at `testls.bit` uses (see §"Reference deployment").

## Resolution algorithm

A wallet attempting CLINK discovery for `<localpart>@<name>.bit` (or
the equivalent `d/<name>` / `id/<name>` form) SHALL:

1. Resolve the Namecoin record per NIP-N1 §"Resolution algorithm".
2. After applying `import` and walking `map`, read
   `nostr.clink_offer[<localpart>]` and `nostr.clink_debit[<localpart>]`
   from the merged Domain Name Object. The scalar shorthand from
   §"Scalar shorthand" MUST be expanded before lookup.
3. If a `noffer` is present, decode it per [CLINK Offers][clink-offers]
   and proceed with the kind 21001 request flow.
4. If an `ndebit` is present, decode it per [CLINK Debits][clink-debits]
   and proceed with the kind 21002 request flow.
5. If both are absent, the identifier has no CLINK endpoint and the
   wallet SHOULD fall back to whatever other discovery mechanism it
   supports (classic NIP-05, LNURL, etc.).

A wallet MAY perform the NIP-N1 lookup once and read all three of
`nostr.names`, `nostr.clink_offer`, `nostr.clink_debit` from the same
merged object. Pubkey verification (NIP-N1) and CLINK endpoint
resolution (this NIP) SHOULD share a cache.

## Security and privacy considerations

- **Identity binding.** The pubkey carried in TLV 0 of the `noffer` /
  `ndebit` SHOULD equal the pubkey at `nostr.names[<localpart>]` of the
  same merged record. A resolver MUST warn the user if these differ,
  because a mismatched pointer is indistinguishable from a payment
  redirection attack mounted by a name-owner whose `d/<name>` record
  was edited but whose Nostr identity was not.
- **Relay-URL binding.** TLV 1 of the bech32 string carries a relay
  URL. If that URL is a `.bit` host, NIP-N3 (TLSA pinning) applies and
  the wallet SHOULD pin per NIP-N3. If it is a DNS host, standard
  WebPKI applies. Wallets MUST NOT downgrade TLS for `.bit` relay
  hints.
- **Reorg handling.** Per NIP-N0, a wallet MUST NOT trust a CLINK
  pointer read from a Namecoin record that has fewer than 12
  confirmations on the publishing transaction, except when the wallet
  is operating in low-stakes mode and the user has been informed.
  Payment-receipt evidence (the kind 21001 `preimage` field for CLINK
  Offers, the kind 21002 `preimage` field for CLINK Debits) provides
  off-chain non-repudiation regardless of subsequent reorg.
- **No leak of payer identity to Namecoin.** The lookup itself is read-
  only and reveals only that someone resolved a public on-chain record.
  Payer identity (the kind 21001 / 21002 `pubkey`) is exposed only to
  the recipient's recommended relay, exactly as in baseline CLINK; this
  NIP changes nothing about that.

## Reference deployment

`testls.bit` carries CLINK pointers via the two-name `import` pattern
described in §"Multi-pointer publication":

- `d/testls` — existing apex, imports `dd/testls`, unchanged by this NIP.
- `dd/testls` — adds one root-level `"import":"d/cl-testls"` entry so
  the merged Domain Name Object pulls in the CLINK fields.
- `d/cl-testls` — new dedicated name carrying only
  `nostr.clink_offer._` and `nostr.clink_debit._`.

After merge, the resolved object for `testls.bit` is:

```jsonc
{
  "nostr": {
    "names":       { "_": "460c25e6..." },
    "clink_offer": { "_": "noffer1qqs..." },
    "clink_debit": { "_": "ndebit1qqs..." }
  }
}
```

— which is byte-for-byte the JSON shape [CLINK Offers][clink-offers]
and [CLINK Debits][clink-debits] specify as the NIP-05 server response,
and which a wallet that already speaks CLINK NIP-05 discovery can
consume without modification beyond accepting `.bit` identifiers.

## Client requirements

A client claiming compliance with this NIP MUST:

- Implement NIP-N1 resolution (or accept that a NIP-N1-compliant
  resolver feeds it the merged Domain Name Object).
- Read `nostr.clink_offer` and `nostr.clink_debit`, applying the
  scalar-shorthand rule from §"Scalar shorthand".
- Reject bech32 strings whose HRP is not `noffer` or `ndebit`
  respectively.
- Validate the local-part / `nostr.names` binding before initiating a
  payment, per §"Security and privacy considerations".

A client claiming compliance MAY:

- Cache the resolved CLINK pointer alongside the resolved NIP-05
  pubkey, sharing eviction policy with NIP-N1.
- Expose both the classic-NIP-05 and Namecoin-NIP-05 discovery paths in
  the same UI surface; the user need not know which substrate carried
  the lookup.

## Service / publisher requirements

A publisher (e.g. a wallet service operator owning a `.bit` name) MUST:

- Publish the bech32 string exactly as produced by a conforming CLINK
  encoder. Truncation or re-encoding MUST NOT alter the TLV payload.
- Ensure that `nostr.names[<localpart>]` and the TLV-0 pubkey inside
  the corresponding `nostr.clink_offer[<localpart>]` /
  `nostr.clink_debit[<localpart>]` agree, or knowingly accept the
  cross-identity-pointer warning from §"Security and privacy
  considerations".
- Stay within the 520-byte Namecoin value limit; factoring CLINK fields
  onto an auxiliary `d/cl-<base>` name via `import` (as in §"Reference
  deployment") is the recommended pattern when the base record is full.

A publisher MAY rotate CLINK pointers by issuing a new `name_update`;
this is cheap and does not require any change to the Nostr identity
itself.

## Relationship to existing NIPs

- **NIP-05 / NIP-N1.** This NIP layers on top of NIP-N1's resolved
  Domain Name Object. The pubkey verification step is unchanged.
- **NIP-57.** A `noffer` with offer-id prefix `zap` (per [CLINK
  Offers][clink-offers] §"NIP-57 zap flow") is the recommended carrier
  for a static zap endpoint anchored in Namecoin.
- **NIP-N2 / NIP-N3.** When the relay-URL hint inside the bech32 is a
  `.bit` host, NIP-N2 (relay discovery) and NIP-N3 (TLSA pinning)
  apply to the WebSocket connection a wallet opens to deliver kind
  21001 / 21002 events.
- **NIP-N4.** A service-attestation set may reference a Namecoin name
  whose record carries `clink_offer`; the attestation does not bind the
  CLINK pointer itself, only the underlying identity.
